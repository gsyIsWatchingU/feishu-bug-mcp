# Fix Bugs 工具增强方案

## 需求分析

用户要求对 `fix_bugs` 工具进行增强：
1. **AI扩写描述**：修复bug时，统一对指定的待解决问题调用飞书AI扩写bug问题描述
2. **待审查状态**：对于不确定的bug（无法自动修复），将状态改为"待审查"

## 现有代码分析

当前 `fix-bugs.ts` 的核心流程：
1. 根据 bug_ids 或索引范围获取目标bug列表
2. 对每个bug调用 `analyzeAndFixBug()` 分析并尝试自动修复
3. 更新bug状态为"已修复待验证"
4. 添加修复备注信息

## 实现方案

### 1. 创建飞书AI客户端

创建新文件 `src/feishu/ai.ts`，实现调用飞书AI助手API进行文本扩写。

### 2. 修改 fix-bugs.ts

主要修改点：
- 在处理每个bug之前，调用飞书AI扩写bug描述
- 如果无法自动修复（`fixApplied` 为 false），将状态改为"待审查"而非"已修复待验证"

### 3. 更新配置

在 `config.ts` 中添加"待审查"状态到状态白名单。

## 关键实现细节

### 飞书AI扩写API

使用飞书开放平台的AI助手API，调用智能问答接口进行文本扩写：
- API路径: `/open-apis/ai/question_and_answer/v1/ask`
- 请求参数: 用户问题（bug描述）
- 响应: AI扩写后的详细描述

### 待审查状态逻辑

当满足以下条件时，将bug状态改为"待审查"：
- `code_fix_enabled` 为 true
- `fixApplied` 为 false（无法自动修复）
- bug类型不匹配已知模式（内存泄漏、空指针、未定义、无限循环）

## 风险评估

| 风险点 | 风险等级 | 应对措施 |
|-------|---------|---------|
| AI API调用失败 | 中 | 添加重试机制和错误处理，失败时使用原始描述 |
| API调用频率限制 | 低 | 添加请求间隔控制 |
| 扩写结果过长 | 低 | 限制最大长度，截取必要部分 |

## 测试计划

1. 测试AI扩写功能：验证bug描述被正确扩写
2. 测试待审查状态：验证无法修复的bug状态被改为"待审查"
3. 测试正常修复流程：验证可修复的bug状态仍为"已修复待验证"
4. 测试错误处理：验证AI调用失败时不影响整体流程
